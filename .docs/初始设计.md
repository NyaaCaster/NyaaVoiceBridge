# NyaaVoiceBridge 初始设计与架构评估

## 1. 项目目标
在 Linux (macmini) 环境下运行一个轻量、高效的独立后台桥接服务。
通过本机已打通的蓝牙音频硬件（小米音箱 NDZ-03-GA / CS4206 / PipeWire），直接与 AstrBot 中运行的 PixNyaa 机器人进行双向语音对话：
- **音频采集**：通过 PipeWire (`pw-record`) 监听蓝牙音箱拾音器。
- **语音识别 (STT)**：调用本地 SenseVoice-OpenAI-API 服务（`192.168.31.142:5052/v1/audio/transcriptions`）。
- **核心大脑**：通过 OneBot V11 反向 WebSocket 协议直连 AstrBot（`ws://127.0.0.1:6199/ws`），模拟 PixNyaa 的专属会话。继承 PixNyaa 的全部人设、记忆、知识库和插件流水线。
- **语音合成 (TTS)**：由 AstrBot 内装的 `Nyaa猫猫语音` (或对应 TTS 插件) 自动生成语音回复，或者在没有语音返回时回退到本地 TTS。
- **音频播放**：通过 PipeWire (`pw-play`) 输出到蓝牙音箱播放。

脱离 NapCatQQ / 腾讯云等外部依赖，形成纯内网、低延迟的物理 AI 音箱实体。

## 2. 架构方案评估：Systemd 守护进程 vs Python 服务

在 Linux 服务工程化中，“Python 服务”与“Systemd 守护进程”并不互斥，而是互为依托的上下层关系：

### 核心结论
**最佳架构：采用“模块化 Python 异步核心服务” + “Systemd 用户/系统守护进程托管”**。

### 详细对比

| 维度 | 单纯 Python 脚本 (nohup / screen / tmux) | 纯 Docker 容器化 | Python 服务 + Systemd 守护进程 (推荐方案) |
| :--- | :--- | :--- | :--- |
| **硬件与音频交互** | 极佳（直接访问 PipeWire / D-Bus） | 极差（PipeWire socket 挂载、D-Bus 权限穿透极繁琐且易断连） | **极佳**（与宿主机音频子系统同属同一权限与会话层） |
| **开机自启** | 需额外依赖 rc.local 或 crontab，无依赖检查 | 依赖 Docker daemon | **原生支持**（通过 `After=sound.target pipewire.service` 精确控制启动时序） |
| **崩溃自愈** | 进程异常退出直接死亡，需手动重启 | `restart: unless-stopped` 可重启 | **毫秒级自愈**（`Restart=always`, `RestartSec=3s`） |
| **日志规范** | 手动重定向日志文件，无轮转易打爆磁盘 | `docker logs` | **journalctl 统一收集**，自动轮转与高压缩存储，可指定时段查询 |
| **运维体验** | 依靠 kill/ps 暴力管理 | docker 管理 | `systemctl status/restart/stop` 标准控制命令 |

因此：
- **代码实现**：使用标准、高内聚低耦合的 Python 3 异步服务包（`asyncio`, `websockets`, `aiohttp`, `soundfile`/`wave`）。
- **部署运维**：提供配套的 `install.py` / `nyaa-voice-bridge.service`，一键部署并注册为 macmini 的 Systemd 守护进程。
