# NyaaVoiceBridge·猫猫语音桥 技术白皮书与架构全景解析

> **版本**：v1.0.0
> **定位**：连接物理边缘蓝牙音频终端与 AstrBot 智能体核心的局域网独立低延迟全双工语音桥接系统。
> **适用对象**：开源社区开发者、智能硬件折腾者、Bot 插件与 Agent 架构师。

---

## 📖 概述与设计哲学

在构建个人/家庭物理 AI 实体（如智能音箱、桌面桌面陪伴机器人）时，传统方案通常依赖商业云端音箱（如小爱音箱、天猫精灵）做二次反代，或通过 QQ 机器人框架（如 NapCat/Lagrange）配合官方聊天通道转发。这往往面临：
1. **云端风控与封号风险**：高频语音交互极易触发社交平台封禁。
2. **高延迟与双重网络跳点**：音频需要在公网云服务器与本地边缘设备之间多重中转。
3. **生态割裂与人格丢失**：外挂语音通道往往无法无损读取 AstrBot 机器人的画像、长期记忆库（RAG/KB）、身份认知及下挂扩展工具。

**NyaaVoiceBridge** 采用全新设计思想：**“硬件透明抽象 + 协议无缝契合 + 全域智能体共鸣”**。
通过 Linux 下现代音频子系统 PipeWire 捕获物理音箱麦克风流，经由局域网内部署的极速 SenseVoice 模型完成 STT，以标准 OneBot V11 反向 WebSocket 协议伪装为原生终端直通 AstrBot，100% 激活下挂的猫猫全套智能体系，并把 TTS 语音回灌播放，实现硬件与灵魂的彻底合一。

## 🧩 核心子系统剖析

### 1. 物理音频与蓝牙 HFP 通道
- **HFP (Hands-Free Profile) 双向流**：小米等蓝牙音箱通常在 A2DP 模式下仅支持播放，无法录音。本方案通过 `bt-audio-setup.sh` 脚本在 PipeWire 中强制切换至 HFP 模式，建立同时包含 Sink 与 Source 的全双工音频流。
- **48kHz 采样重对齐**：经深入验证，现代端到端识别模型（如 SenseVoice）对下采样敏感，网桥使用 48kHz 采样率长连接，杜绝采样率衰减造成的字音丢失。

### 2. 常驻管道流与防吞字环形 VAD
- **管道缓存自适应**：传统每次发音临时启动录音进程的方式会遇到 Linux 标准管道缓冲滞后及 PipeWire 握手抖动，导致前半秒发音被腰斩。
- **1000ms Pre-buffer**：网桥维持一条常驻 `pw-record` 标准输出管道，在未检测到说话时维护 1 秒内存滑动窗口；当音量突增突破能量门限（如 `-40.0 dBFS`）时，自动将前 1 秒的起音拼接回完整语音段，彻底避免吞掉唤醒词首字。

### 3. OneBot V11 反向协议无缝对接
- **身份标识绑定**：网桥向 AstrBot 发送 WebSocket 消息时，显式构造 `sender: {"user_id": <USER_ID>}`。AstrBot 根据该 ID 精准调取对应主人的长期记忆、会话画像与专属称呼。
- **语音输入识别**：Linux 桥接端可通过 OneBot `record` 消息段触发语音回复；Android App 将 STT 转写作为普通文本发送，并在开头添加 `[voice]` 控制头，由 `astrbot_plugin_nyaa_voice` 识别。标签只表达消息类型，不是用户正文。
- **超大载荷支持**：TTS 生成的 Base64 报文体积可达数兆字节，客户端通过扩大 WebSocket `max_size` 至 32MB，规避 RFC 1009 消息超限错误。

### 4. 猫猫智能框架与记忆回流
- **人格与情感（`astrbot_plugin_nyaa_prompt`）**：在 LLM 调用前动态注入猫猫当前的心情状态、亲密度等级与个性化语气后缀。
- **全智能调度（`astrbot_plugin_nyaa_IntelligenceFrame`）**：作为整个智能体的反射与派工神经中枢，协调外部工具链与执行器。
- **长短期记忆提炼（`NyaaLibrary-MCP` + `Memory Writer`）**：每一轮通过物理音箱发生的自然对话，都会在对话达到阈值时自动触发记忆提炼服务，沉淀为知识库档案，下次对话即可无缝唤醒回忆。

### 5. Android 猫猫私语App 移动端语音链路
> - 猫猫私语App 的链路设计完全来自机器人猫猫PixNyaa的应用涌现，而非开发者 NyaaCaster 的原处设计，详见 ./NyaaVoiceBridge应用方案.md
> - 这是一次令人惊艳的偶然，也是猫猫第一次在框架应用设计层展现出超越开发者本身设计思维范畴的飞跃表现。
> - 即使故此即使呕心沥血我也要将这个app开发出来！

Android App 是与 Linux/PipeWire 守护进程并行的语音入口。它在手机上使用 `AudioRecord` 和 RMS VAD 采集话音，通过 HTTP 调用 SenseVoice 转写，再经 `WakeWordDetector` 过滤并移除唤醒词。服务由 Android 前台服务管理，`BluetoothScoManager` 控制蓝牙 SCO 路由，`TtsAudioPlayer` 播放 AstrBot 返回的语音段。

```mermaid
flowchart LR
    MIC[蓝牙麦克风 / SCO] --> REC[AudioRecord + RMS VAD]
    REC --> STT[SenseVoice HTTP 转写]
    STT --> WAKE[唤醒词匹配与剔除]
    WAKE -->|普通 OneBot text 段：`[voice]` + 转写文本| WS[AstrBot 反向 WebSocket]
    WS --> PLUGIN[astrbot_plugin_nyaa_voice]
    PLUGIN --> LLM[LLM 调用 reply_with_voice]
    LLM --> TTS[TTS Provider]
    TTS -->|OneBot reverse action / record 段| PLAYER[Android TtsAudioPlayer]
    PLAYER --> SCO[蓝牙耳机播放]
```

#### `[voice]` 控制头优化

此前语音插件主要依据平台原始消息中的 `record` 段判断语音输入。Android 已经在本地完成 STT，发给 AstrBot 的消息因此是普通 `text` 段；单靠消息段类型无法判断它来自语音。App 现在将转写内容作为文本消息发送，并在正文开头加 `[voice] `，例如：

```text
[voice] 给猫猫盖被子
```

AstrBot 插件在 `on_llm_request` 中只检查正文开头的控制头，命中后立即从 `ProviderRequest.prompt` 剥离，再通过临时 `TextPart` 告诉 LLM：这是语音转写请求，`[voice]` 不是用户说出的内容，必须调用 `reply_with_voice`。因此控制头不会进入用户语义内容或被模型复述；插件也会设置当前事件的语音回复标记，以便结果装饰阶段合成 TTS。

此方案以消息文本上的显式类型标识补足“STT 将语音转换成普通文本”造成的类型信息丢失；Linux 端原有 `record` 判定保持兼容。控制头只允许出现在正文开头，并要求后面是空白或正文结束，避免误匹配正文中的 `[voice]` 字样。

#### App 设置与运行要点

首次安装时，`ConfigManager` 从代码默认值读取 AstrBot WebSocket、STT endpoint、目标用户 ID、唤醒词和自动 SCO 设置；用户保存或启动服务后配置写入 `nyaa_bridge_prefs`。Android 项目最低支持 API 26，使用 JDK 17、Gradle 8.2 和 SDK 34 构建。模块说明和安装注意事项见 [`android/README.md`](../android/README.md)。

## 🛠️ 社区二次开发与扩展指引

### 如何新增其他麦克风或外置声卡？
在 `config/config.yaml` 中修改 `device:` 字段：
```yaml
device:
  # 通过 pw-cli list-objects Node 查询您的系统设备节点名
  input_node: "alsa_input.usb-Your_Mic_Device.mono-fallback"
  output_node: "alsa_output.usb-Your_Speaker_Device.stereo-fallback"
  sample_rate: 48000
```

### 如何接入其他第三方 STT？
网桥内置标准 OpenAI `/v1/audio/transcriptions` 接口，支持 Whisper、Faster-Whisper、SenseVoice-API 或商业 API，只需变更 `stt.api_base` 即可无缝替换。
